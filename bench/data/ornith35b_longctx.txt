################################################################
# MTP SPECULATIVE DECODING, 2026-09-13
################################################################
vLLM auto-builds the draft config for model_type qwen3_5_moe: it rewrites the
type to qwen3_5_mtp and reads mtp_num_hidden_layers (=1, in text_config) for
n_predict. No separate drafter download. Enable with:

  --speculative-config '{"method":"mtp","num_speculative_tokens":K}'

Log confirms it: "Detected MTP model. Sharing target model embedding weights
with the draft model." KV cache drops from 625,916 tokens to ~400-411k,
because the drafter takes memory. Startup cost rises to ~170 s (69 s of
torch.compile) from ~40 s.

                      no MTP    MTP k=2   MTP k=1 + batch 8192
decode C1             122.49    150.52    141.76
decode C4             345.36    273.06    260.65
decode C8             597.32    251.95    572.35
prefill ~8.9k          9145      8917     11013 / 11183
decode at 24k ctx     117.8      74.4      69.4
J/token C1             1.127     0.942     0.966
J/token C8             0.412*    0.321     0.232
  (*the 80B's figure; Ornith no-MTP C8 was 0.241)

=== Finding 1: the C8 collapse was a scheduler default, not MTP ===
Enabling speculative decoding makes vLLM warn:
  "max_num_scheduled_tokens is set to 2048 based on the speculative decoding
   settings. This may lead to suboptimal performance."
At k=2 with that default, C8 fell to 251.95 tok/s and the card drew only
80.9 W at 1170 MHz: it was stalling, not computing. Passing
--max-num-batched-tokens 8192 restored C8 to 572.35, within 4% of no-MTP,
and pushed prefill to 11,183 tok/s, the best figure measured on this card for
any model. If you enable MTP, raise the batch budget in the same breath.

=== Finding 2: MTP helps single stream and hurts long context ===
C1 gains 16-23%. Decode at 24k context loses ~40% in BOTH k=1 and k=2, so it
is not a tuning artefact: the verify step costs more as the context grows,
and acceptance does not pay for it. C4 also stayed down ~25% in both.

=== How to pick ===
single-stream, short prompts  -> MTP k=2          (150.5 tok/s)
long context                  -> no MTP           (117.8 tok/s at 24k)
high concurrency              -> no MTP, or k=1 + batch 8192 (597 / 572)
best prefill                  -> k=1 + batch 8192 (11,183 tok/s)

There is no single best configuration. Match it to the traffic.

# REASONING BUDGET, 2026-09-13  (bench/reasoning_budget.py)
################################################################
Server: Ornith FP8, vLLM 0.27.1, --reasoning-parser qwen3, no MTP,
VLLM_USE_V2_MODEL_RUNNER=0 (the V2 runner rejects thinking_token_budget).
Sampling: temperature 0.6, top_p 0.95, top_k 20 (model card, general tasks).
10 prompts x 6 conditions x 3 reps = 180 requests, 0 errors.
8 graded prompts (24 graded answers per condition), 2 open-ended.

condition         correct  empty  reasoning med  max   crt   apples
unbounded           24/24      0             96   447   3/3   3/3
thinking_off        20/24      0              1     1   2/3   0/3
budget_1024         24/24      0            101   634   3/3   3/3
budget_256          22/24      0            102   257   1/3   3/3
budget_64           22/24      0             65    65   1/3   3/3
max_tokens=256      19/24      7            100   256   0/3   3/3

(reasoning tokens = completion_tokens minus the answer's tokenized length;
 unbounded runs had max_tokens 16384 and none hit it)

Grader note: the first pass graded 4 correct crt answers as wrong, because
it took the LAST number in the reply and the model follows "**301**" with a
worked check. Regraded on the first number; script fixed.

=== 1. It does not overthink on this set ===
Unbounded median 96 reasoning tokens, max 447, zero length-stops against a
16k cap. At 122 tok/s that is ~0.8 s median, ~3.7 s worst. The longest
thinking was the number-theory prompt (433) and, notably, the open-ended
one-sentence prose prompt (339): it deliberates more over how to phrase an
opinion than over arithmetic. Chit-chat thinks ~55 tokens.
CAVEAT: short, single-turn, checkable prompts only. Its training target is
long agentic coding (the card evaluates with max_new_tokens up to 131,072),
which this does not exercise. "Needs limiting" may hold there; unmeasured.

=== 2. thinking_token_budget is an exact hard cap ===
budget 64 -> max 65 reasoning tokens; budget 256 -> max 257 (the budget
plus the forced </think>). vLLM masks logits to force the end-of-thinking
token once the budget is spent, then the model writes its answer.
budget 1024 never bound on this set (the one 634 run finished on its own).

=== 3. The cost of limiting is silent, confident wrong answers ===
Budget 256 and 64 broke only the hardest prompt, and not with an empty reply
or a hedge: 4 of 6 answered "121" flatly, where the answer is 301.
Disabling thinking was worse than any budget: 0/3 on the apples word problem
("5", "5", "6") plus one crt miss. A truncated thought produces a confident
wrong answer, not an "I'm not sure". For an honesty-first deployment that
matters more than the accuracy number.

=== 4. Never limit it with max_tokens ===
max_tokens=256 with no thinking budget returned 7 of 30 EMPTY answers with
finish_reason=length, and one truncated code block. The cap landed mid-think,
so there was no answer to return. This is the same silent empty-response
trap recorded for the 27B. Use thinking_token_budget, which bounds the
thought and still leaves room for the answer.

=== Recommendation ===
If a limit is wanted, thinking_token_budget ~1024 cost nothing here. 256 is
survivable for easy traffic but silently wrong on hard problems. Do not
disable thinking, and never use max_tokens as the limit.
